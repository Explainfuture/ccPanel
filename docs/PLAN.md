# ccPanel 实施计划

## 目标与范围

先实现可自托管的 Mixpanel 核心替代：事件接入、用户识别、事件探索、趋势、漏斗、留存、分群和仪表盘。完整 Mixpanel 功能等价不是首版承诺。基础架构已确认，以 [架构 v2](ARCHITECTURE.md) 与 [PRD v1.1](PRD.md) 为实施依据；用户已授权持续开发、在试验机安装依赖和部署测试。实时实现与验证状态见 [PROGRESS.md](PROGRESS.md)，未通过生产验收前只作试验预览。

## 阶段与验收门槛

1. 架构评审（基础方案已确认）：使用架构 v2 的可编辑图，包含 SDK 队列和浏览器送达边界，历史图片不作为实施规格。
2. PRD（v1.1 已生成）：定义事件模型、身份关联、漏斗/留存口径、迟到事件、时区、公司级租户隔离、操作权限、数据删除和验收场景。同公司成员可查看全部项目数据，不做员工/部门/项目数据范围；默认参数先用于实现与验证。
3. 基础工程：pnpm workspace；apps/web、apps/api、apps/worker；packages/sdk-browser、sdk-node、schema、query-core、ui；infra 与 docs。固定依赖版本、迁移流程、CI。
4. 接入闭环：SDK 批量发送、持久队列与重试；Hono 校验鉴权；Kafka；消费幂等落库；原始事件查询。验证超时重发、进程退出与消费重放不会重复计数。
5. 核心分析：先趋势与仪表盘，再漏斗、留存与分群；定义数据集对账，验证身份合并与迟到事件。
6. 稳定性：压测、故障注入、限流背压、DLQ 重放、备份恢复、租户隔离与查询预算。产出实测容量报告。
7. 单机试运行：获取服务器规格后配置 Docker Compose、TLS、资源上限、卷、备份、监控和升级回滚；演练恢复后再接真实流量。
8. 扩容：根据实测瓶颈分离接入、消费者、分析查询与存储，升级 Kafka 多副本、PostgreSQL 高可用；分析量超出 PostgreSQL 预算时另行评审分析存储。

## 容量与 SLO 待确认

已知试验机：Ubuntu 24.04、1 vCPU、约 961 MiB RAM、1 GiB Swap、20 GB 磁盘；重装后检查时约 16 GB 可用。资源数据为检查快照，不是容量承诺；本仓库不保存服务器密码、登录密钥或其他凭据。

仍待确认：磁盘类型、带宽、峰值事件/秒、平均事件大小、日事件数、业务保留天数、查询并发、可接受分析延迟、RPO/RTO、预算。未取得压测结果前不承诺 QPS 或上线日期；试验机允许尝试低负载完整链路，不作为生产高可用环境。

估算：原始日数据 = 平均 EPS × 平均字节数 × 86400；另外计入索引、WAL、Kafka 副本/保留、备份和安全余量。Kafka 保留窗口必须覆盖最长故障恢复与追赶时间，按磁盘容量校验。

## 拟定验收方式

- 每个生成事件有稳定 ID；对账发送、确认、Kafka、数据库、DLQ 数量，确认事件均能解释去向。
- 杀死消费者、模拟数据库不可用与提交 offset 前崩溃：恢复后重放，分析计数不重复。
- Kafka 不可用、ISR 不足、磁盘满：接入不虚假确认成功；SDK 保留待发事件并报告队列耗尽。
- 压测同时包含接入与查询，记录 p95/p99、错误率、消费积压、追赶时间、CPU、内存、磁盘。
- 恢复演练验证备份可用；单机损毁风险与生产多副本容灾结果分别记录。
